## Design

Keep PostgreSQL Markdown cells, cell IDs, the existing notebook save/history APIs and managed metadata as the only content authority; add no HTML database store, implicit save or migration. A journal-level mode applies to its cells, while the top toolbar targets the last focused cell and its retained selection. The Japanese fixed tab is 実験ノート and English remains Lab Note. Ordinary ipynb retains its existing three controls.

### Dedicated journal rich authoring (new change, pending approval)

Use a maintained schema-based ProseMirror Markdown editor, not document.execCommand or arbitrary contentEditable innerHTML round trips. Its schema supports paragraphs, headings, lists, quotations, links as inert editor marks, inline code and strong/em/strike. Keep raw source separate from the parsed view: create/toggle/focus never serializes or changes dirty state. Only real document edits produce Markdown. On actual rich edits, equivalent Markdown delimiters/spacing may be normalized; content, cell identity and stored metadata must not be discarded. Undo/redo remains scoped to the current editor; changing view preserves the draft but need not retain the old rich editor's undo stack.

Use the same editor transaction/history mechanism for literal Text mode, with a single plain code-text projection of the complete source and no Markdown transforms. This keeps timestamp insertion and undo/redo selection-aware without document.execCommand, pasted HTML, or an unrelated text-editor engine. The mode still displays raw Markdown, not code execution.

Pinned proposed application additions: prosemirror-model1.25.13, prosemirror-state1.4.4, prosemirror-view1.42.9, prosemirror-markdown1.13.9, prosemirror-commands1.7.2, prosemirror-history1.5.1, prosemirror-inputrules1.5.1, prosemirror-keymap1.2.3 and prosemirror-schema-list1.6.0 (MIT). Reuse the already pinned markdown-it15.0.3; its parser may coexist with the Markdown adapter's transitive14.x dependency. Do not install application additions until approval; only the external session spike has a separate manifest/install.

Apply the existing64KiB UTF-8 per-cell source budget, including metadata, before rich parsing and at save. Limit complex rich preview nodes to100 per cell and reject an over-budget rich projection with a visible error while preserving the original in editable Text mode; never truncate content to fit. Plain-text paste/drop must reject invalid or over-budget input explicitly without modifying the draft. No-text clipboard/file drops report an unsupported-input error rather than succeeding with an empty replacement.

Reuse strict front-matter parsing and expose a validated exact prefix/body split. Rich editing changes only the body and retains the original BOM and YAML prefix byte-for-byte until the existing explicit save applies its saved metadata baseline. Invalid front matter produces a visible error and leaves editable Text mode available; do not strip invalid YAML or silently start an empty document.

Tables, fenced code/Mermaid, math and owned images remain source-backed non-editable rich preview nodes when their exact source cannot be represented safely by the editable schema. Render them only through existing bounded scientific/image mechanisms, preserving their source on unrelated edits. Their internals remain editable in Text mode. No arbitrary image src, active pasted HTML, external fetch or direct SVG enters the rich DOM. Clipboard/drop ingestion is bounded plain text interpreted as inert Markdown, never trusted HTML; editor links do not navigate automatically.

Heading buttons toggle the active block's level1/2/3; bold/italic/strike use selection-aware marks and collapsed-caret stored marks. Prevent pointer toolbar focus loss while retaining keyboard access. Timestamp uses new Date().toISOString(), inserts at the retained selection in either mode, and is user-requested content rather than a trusted timestamp service. Without a focused cell, target the first Markdown cell; with no cells, an explicit timestamp action creates exactly one. Disable modifying controls and editor transactions for archived/busy state; mode switching remains a read operation. Show errors through existing localized alerts.

Risk stages: contract covers actual direct editing versus preview; trusted inputs cover validated metadata and inert paste/links/images; execution covers selection-aware transactions, composition, disabled state and bounded parsing; verdict exposes parser/render/save failures; evidence history retains exact unedited source and the saved YAML baseline; integration covers fixed labels, independent drafts, save/history, scientific rendering and ordinary ipynb regression. ### Existing ordinary ipynb authoring and metadata

The current carrier is labeled 電子実験ノート/ELN. The latest explicit user decision retains individual movable/closable notebook viewer tabs under `REQ-LAYOUT-002`; authoring modes and metadata must survive that carrier correction without changing notebook IDs, source, save APIs or stored history. Historical Lab Note test titles and internal identifiers do not authorize a fixed-tab contract.

Use the existing Notebook save operation, not a second cell-save API. Each Markdown cell has independent source/rendered/edit state; viewing alone never marks the document dirty. Source/rendered modes share the existing escaped/sanitized viewer, and code/raw-cell editing is unchanged. Japanese buttons are 原文を表示, レンダリングを表示 and 編集; English buttons are Show source, Show rendered and Edit.

The shared Markdown utility parses YAML with pinned yaml2.9.1, rejects duplicate keys, unknown tags and alias expansion, and limits front matter to64 KiB UTF-8 including delimiters and optional3-byte BOM, on both read and rewritten output. Preserve other YAML fields and the Markdown body; ordinary YAML formatting/comments may be serialized differently when the managed header is updated. Notebook's existing64 KiB source-per-cell budget includes YAML and is checked before submission. History is never silently truncated to fit. A configured display name is browser-local operational preference, separate from project ownership.

The managed header is:

```yaml
---
aira:
  created_at: 2026-11-11T00:00:00.000Z
  updated_at: 2026-11-11T00:00:00.000Z
  editor_identity: self-declared
  editor_history:
    - edited_at: 2026-11-11T00:00:00.000Z
      editor: Example Editor
---
```

Times are UTC ISO strings from the writing browser's clock, not a trusted timestamp service. For legacy content without tracked metadata, the first tracked upload/save initializes dates and history; earlier creation dates/editors are unknown and must not be invented. Incoming file metadata/history is unverified self-declared content, not an audit authority. For an edited cell, saved metadata is the baseline rather than user-edited history in the draft.

Workspace uploads construct a new Blob from the updated bounded header and the original file-body bytes, avoiding a full-file text read or changes to the local original. Raw upload APIs, SDK/execution artifacts and imported records remain byte-preserving; they are not silently rewritten or assigned a human author. Existing immutable file versions are unchanged. Metadata in existing Markdown cells is adopted on explicit Notebook save; no background migration or hidden save occurs.

The renderer removes valid front matter only for formatted output; stored/raw source remains complete. Native Node24 math workers use an explicit `.ts` helper import, permitted by the no-emit TypeScript configuration; heap/output/time limits remain unchanged.

A leading BOM is an encoding marker even without front matter: body display excludes it, while explicit metadata rewriting preserves it at the start of stored source. `TEST-MARKDOWN-004` includes a headerless body-display case and exact/+1-byte read-budget controls. `TEST-RENDER-005` covers normal and BOM-prefixed managed headers through the renderer. These declarations are acceptance conditions, not claims that currently failing later assertions have passed; full output/body/original-file assertions remain unproven until Green. `TEST-MARKDOWN-002` also exercises unchanged tracked re-upload; `TEST-MARKDOWN-003` includes trimming and80/+1 Unicode-code-point controls. Browser persistence/fallback still requires GUI observation.

## Observed defaults and known gaps

- An untouched legacy cell without managed metadata is adopted on its first explicit Notebook save, even when only another cell changed. Its `created_at` means first tracked time, not an invented historical creation date. Once tracked, exact unchanged source returns byte-identically without appending an editor. Source change means byte-different source.
- With a saved cell baseline, valid draft edits to managed `aira` history are replaced by the saved history before appending the current editor; this is the documented protection rule, not invalid-YAML recovery. Ordinary YAML fields/body remain editable. Invalid YAML/managed metadata still fails explicitly.
- Every explicit workspace upload creates a newly tracked immutable version and appends the configured editor, including re-uploading unchanged tracked input. There is no saved-version baseline on the upload path.
- The observed validator counts Unicode code points:80 supplementary characters are accepted,81 rejected. The earlier unexecuted UTF-16 assumption was incorrect and was corrected before approval; its failed assertion is not a producer-defect Red. Existing HTML typing remains more restrictive (`maxLength=80` counts UTF-16 units); preserve/document this limitation rather than silently changing accepted stored history. Old valid theme/locale objects missing a name retain those choices and gain `local`. An invalid provided name makes stored preferences invalid as a whole: default Light/Japanese/local plus a visible error, not partial silent recovery. Settings rejects invalid new input before persistence.
- BOM defect (confirmed, open): `markdownUpload` currently drops BOM bytes during prefix decoding but computes a raw-file offset from the decoded header. A BOM plus front matter yields an extra `--` line in the body; a BOM without front matter moves inside the newly prepended header/body boundary. Cell metadata rewriting can also drop or move a BOM. Two actual upload counterexamples failed in `integrated-markdown-bom-observation-red.log`. The intended output on uploads AND cell updates is optional original BOM, then managed header, then exact original body; a BOM occurs only at file byte0/source character0. UTF-8 upload bytes begin EF BB BF 2D 2D 2D 0A; cell source begins U+FEFF followed by `---` and LF. `markdownBody` and rendered display exclude a BOM-prefixed valid header. `TEST-MARKDOWN-004` checks raw prefix/body bytes on both upload and cell paths, with/without existing front matter, and unchanged tracked-cell preservation. No production fix or Green is claimed here.
- A new unsaved cell may contain incoming self-declared metadata; its first explicit save adopts that unverified history, never authenticated authorship. Subsequent saved history is authoritative only as the application's saved baseline, not a tamper-proof audit authority.
