## Design

PostgreSQL jsonb + optimistic revision; per-cell aira language and shared-variable descriptors. Immutable run snapshots are separate from the current cell-output projection.
Ordinary ipynb Markdown cells default to rendered display and provide independent source/rendered/edit controls under REQ-MARKDOWN-001. The project journal occupies the fixed second Lab Note tab under REQ-LAYOUT-002 and follows the editable Text/direct rich-rendered controls in REQ-MARKDOWN-004/005; the independent ipynb manager and movable/closable ipynb tabs retain existing research identities. Explicit saves maintain YAML timestamps and self-declared editor history under REQ-MARKDOWN-002; viewing alone never changes source or revision. The existing per-cell source budget includes YAML. Editing a tracked cell preserves its saved history baseline; an unchanged tracked source is not stamped again. Archived cells remain readable with all content mutations disabled.
Per-Notebook draft/busy close and client archive guards are owned/tested by REQ-LAYOUT-002 and TEST-LAYOUT-005/006; server archive/content authority remains REQ-PROJECT-002/005. These cross-feature client guards do not replace this feature's optimistic save checks or claim that a server can inspect unsaved browser drafts.
The optimistic revision counter, immutable executed snapshots and self-declared YAML editor history alone do not constitute a complete notebook-edit version store. Past-edit browsing, diffs, restoration and derived local Git are owned by [notebook-history](notebook-history.md), not evidence of this feature's completion. Requirements/design approval and current implementation qualification remain separate stages.
No long execution DB locks. A valid run binds the immutable confirmed snapshot; later edits yield a retained completed run with stale projection, not an invalid execution. Cell projection returns 409 and kernel stops; restart never deletes records.

### Independent project Lab Note

Reuse the existing nbformat document, revision, saved-version/outbox and Markdown editor internally; a shared representation does not make the journal an ordinary user-created ipynb. Add `project_lab_notes` with project primary key, unique notebook ID and a composite foreign key to that notebook's project/actor link. The application role can read but cannot insert/update/delete these associations.

A migration-owned function with fixed `pg_catalog` search path and schema-qualified relations provisions an empty Markdown-only notebook, its association, initial `create` version/hash and Git intent. Revoke direct PUBLIC/application execution. An AFTER INSERT trigger on `chats` invokes it in the same project/chat transaction; rollback removes all dependent records. The migration backfills existing projects in deterministic project-ID order under the writer advisory try-lock, using the same routine. New journal creation is a real new event at current server time with unknown/system editor, not reconstructed historical research. Preserve all preexisting notebooks and history, even those named Lab Note/ELN.

GET `/api/projects/:projectId/lab-note` resolves the owned association read-only, including archived projects; it never creates research or repairs missing data implicitly. Missing associations fail explicitly. Existing scoped notebook save/PATCH/version routes operate on the resolved identity; validate Markdown-only cells in the shared transaction path before every journal content mutation, including accepted proposals and restoration. Migration-owned triggers also reject non-Markdown journal documents in `notebooks` and saved journal content in `notebook_versions`, including direct application-role writes. Ordinary ipynb code/raw cells remain supported. Association creation and independent restore validate the type invariant as well, so insertion order cannot bypass it. Ordinary create/import cannot nominate a journal identity. Exclude the journal from ordinary notebook lists; internal server classification comes from the immutable association, not request metadata, name or array order. Keep the existing size limits, conflict checks, inert previews, history and no-external-push policy. Reuse the version store rather than introducing a second journal audit subsystem.

Backup/restore must include the association relation and validate journal cardinality, actor/project/chat scope, Markdown-only current and historical documents, and exact current version/head. The existing restore first creates the current schema and then uses data-only `pg_restore`. In its new private destination only, disable the named journal-provisioning trigger around that data load and re-enable it in `finally` before final validation; never disable triggers in the source or globally disable foreign-key/type constraints. A restore failure or inability to re-enable is not success and never starts the restored application. Preserve the existing schema fingerprint policy: an older-schema archive is rejected explicitly before destination creation, not automatically upgraded. An approved upgrade may instead operate on a separately restored compatible copy; no old archive is modified. Required tests cover exact journal/history round-trip, a missing association, invalid historical cell type, the trigger's re-enabled behavior and the unchanged schema refusal.

Risk-stage coverage for the replacement: contract separates one journal from multiple ipynb; trusted inputs use server associations and scoped ownership; execution uses atomic fenced writes/DDL and no journal code cells; verdict exposes missing/load/save/Git failures; evidence history preserves old records and actual initial creation; integration covers migrations, project creation, lists/API dispatch, editor guards, backup/restore and deployed Demo hashes. All six stages apply.

## Assumptions / risks

At most 100 cells, 64 KiB source per cell; sharing supports explicit names only. Export/reimport and conflict tests retire schema assumptions. No regulatory signatures.
