# AIRA Nexus 要件定義書

更新日: 2026-11-11

本書は、機能と制約を日本語で整理した参照文書である。2026-11-11の独立Lab Note変更は、承認済み要件・設計に基づく実装・機能検証・既存環境への移行を完了した。全体の正式資格付けは未完了である。個々の要件ID、EARS条件、反例、試験との対応は [`.sdd/specs/`](../.sdd/specs/) を正とし、本書で独立した要件番号や承認状態を新設しない。構成・保存処理は [設計書](design.md) を参照する。

## 1. 目的と対象範囲

### 実験ノートの直接編集（実装・機能検証済み）

中央固定タブの日本語名を「実験ノート」に短縮し、英語は「Lab Note」のままとする。実験ノート上部には「Text表記」と「Markdownレンダリング表記」の2ボタンを置く。TextではMarkdown原文も編集でき、レンダリング表記では表示された文章を直接編集する。入力欄とプレビューを分ける方式ではない。

両モードでタイムスタンプ挿入を提供し、レンダリング表記では `#`、`##`、`###`、太字、斜体、打消し線のボタンを提供する。選択範囲またはカーソル位置に適用し、タイムスタンプはブラウザ時計のUTC ISO8601表記とする。表示だけでは保存・履歴追加を行わず、既存の明示保存、メタ情報、版・競合・未保存確認を維持する。通常ipynbとファイルビューは変更しない（REQ-MARKDOWN-004/005、REQ-LAYOUT-002）。

数式・Mermaid・表・画像等の複雑な部分は安全な原文付きプレビューとして保持し、内部の編集はTextで行う。実際にリッチ編集した場合は同等なMarkdownの区切り記号・空白を正規化することがあるが、表示切替だけではBOM・YAML・本文を変えない。リッチ表示はセル全体のUTF-8で64 KiB、複雑プレビュー100個を上限とし、超過・無効なYAMLはTextで修正できる。アプリ全148試験に合格したが、全体の正式資格付け完了を意味しない。

研究プロジェクトごとに、単一のAIチャット、1つの独立した実験ノート（Lab Note）、複数作成可能なipynb、入力・生成ファイル、実行記録を関連付けてローカルで管理する。Lab Noteはipynbの管理画面ではなく、プロジェクト専用の記録文書である。AIの提案、コード実行、外部への研究内容の送信は、それぞれ明示的な確認を必要とする。

対象は単一のローカル所有者が利用する開発実装である。明示的に設定した信頼済みLANからの利用には対応するが、アプリのログイン認証、TLS、利用者別の分離、インターネット公開は提供しない。編集者の表示名は認証情報ではない。

## 3. 保存・表示に関する制約

バックアップと独立復元には専用ノートの関連・本文・全保存版も含め、1プロジェクトに1件であること、Markdown専用制約、現在版との一致を検査する。復元時に別IDの空ノートを自動作成せず、復元後は新規プロジェクトの自動作成機構を再有効化する。旧スキーマのアーカイブは従来どおり復元先作成前に明示拒否し、暗黙に変換しない（REQ-NOTE-006）。

| 対象                             | 制限・拒否条件                                                                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 生ファイルアップロード           | 1ファイル100 MiB以下。プロジェクトの不変ファイル割当は保留中を含め2 GiB                                                                   |
| 実行入力                         | 合計256 MiB以下。同名衝突、他プロジェクトのID、不正ハッシュを拒否                                                                         |
| テキストプレビュー・科学描画入力 | 先頭64 KiB。省略は明示し、元ファイルは変更しない                                                                                          |
| ノート                           | 最大100セル。各セルのソース64 KiBにはYAMLを含む                                                                                           |
| 保存履歴の参照                   | 一覧は最大50件／ページ。原文・差分APIは12 MiB以下。各原文・メタ情報表示は64 KiBまでとし、省略バイト数を明示する。DBの保存版は切り捨てない |
| Git処理                          | 1コマンド30秒、標準出力2 MiB、標準エラー64 KiB、標準入力512 MiB。自動試行は最大3回。処理上限で失敗してもDB保存版を保持する                |
| YAML                             | ヘッダー64 KiB以下。重複キー、未知のタグ、エイリアス展開、不正な管理メタ情報を拒否。履歴を黙って切り捨てない                              |
| PNG/JPEG                         | 入力10 MiB以下、各辺8192 px以下、3200万画素以下。署名・デコード検証後にPNGとして再出力                                                    |
| SVG                              | ソース256 KiB以下、2000要素以下。上記画素制限、2秒のラスタライズタイムアウト、出力PNG 10 MiB以下                                          |
| Mermaid                          | 1ビュー最大10図、1図のソース8 KiB UTF-8以下、生成SVG 1 MiB以下。フローチャートの辺数設定は100                                             |
| 数式                             | 1式8 KiB、1ビュー100式、展開1000回、出力1 MiB、Worker処理1秒を上限とする                                                                  |

生HTML、実行可能なSVG、外部URL・data URL・file URLの画像を研究本文へ直接埋め込まない。同じプロジェクトの画像を表示するローカル取得は許可するが、外部画像取得や暗黙のAI送信は行わない。

## 4. メタ情報と履歴の保証範囲

- 作成日・最終編集日は、書き込み元ブラウザのUTC時刻である。信頼できる時刻認証ではない。
- 未追跡の既存データは、以後のGUIアップロード・明示保存から記録する。過去の日付・編集者は復元・捏造しない。
- 編集者名は自己申告であり、ログイン済みユーザーの本人性を保証しない。
- YAMLは編集可能な研究データであり、改ざん不能な監査ログではない。
- 現在の保存リビジョンは競合検出に利用する。実行履歴、YAMLの編集者記録、DBの保存版本文は別の記録である。
- 既存データの移行では現在版だけをベースラインとして登録する。表示する記録時刻は移行時刻、以前の編集者は不明とし、失われた過去版を捏造しない。
- 通常保存の日時・実施者はサーバイベントへ記録する。過去版の復元では当時のYAMLをそのまま保持し、今回の自己申告実施者と復元元は別の新規イベントへ記録する。
- DBとGitを物理的に同時確定する保証はない。DBを正本とし、Git完了は検証・確認後だけ表示する。未出力・失敗はDB保存失敗と混同しない。
- 履歴は全版保持し、容量は増加する。容量監視とバックアップの運用は別途必要である。解消不能なGitロックや不整合は、旧リポジトリを残した新世代への再構築で扱う。

本文の版スナップショット、差分、確認付き復元、ローカルGit自動出力は実装・配信済みである。詳細は [notebook-history](../.sdd/specs/notebook-history.md) を正とする。

BOM付きMarkdownのGUIアップロード・セル保存では、先頭のUTF-8 BOMを管理YAMLより前の符号化プレフィックスとして維持し、本文へ移動させない。既存ヘッダーの有無の両方で本文を保持し、ローカル元ファイルと既存の不変バージョンを書き換えない。修正は `TEST-MARKDOWN-004` の実際のRed／Green、メタ情報試験10件、4種類の隔離変異で確認した。履歴はサーバが受信した本文を保持・復元するもので、過去にGUIが変換した元バイト列は推測しない。

## 5. 試験・承認の扱い

要件と試験の詳細な対応は各仕様書のTest列を参照する。履歴管理ではDB・Gitの45件、履歴画面と関連レイアウトの5件、既存workspace E2Eの1件、全体の型チェック・lint・ビルドが合格した。既存のノート・提案・入出力・診断も回帰確認し、DB/Gitの隔離変異試験と画面の下書きガード変異試験で反例検出を確認した。

配信後、LAN上の実ブラウザで履歴・原文・差分・Git完了表示を確認した。Demoはリビジョン1、実行記録0件、本文と不変ファイル6件のハッシュを維持し、現在版だけのベースラインが追加された。

人間承認済みの仕様書と承認ハッシュは固定スナップショットであり、仕様書内の実装前メモは承認時点の記録である。既存の計画・ゲート設定を維持し、全22タスクの最新の正式receiptと、固定した対象・環境・試験行列に対する連続2回の全体gate・既存E2Eの合格を全体資格付けの条件とする。後から反例を適用して更新した証拠は、実装当初のTDD順序を復元したものとは扱わない。個別の機能検証、全体資格付け、人間によるリリース承認を区別し、技術的合格から公開許可を推定しない。

固定行列と対象ハッシュは `.sdd/qualification/manifest.json`、実際の判定と各回の証拠は `.sdd/qualification/report.json` に記録する。対象環境以外への移植、認証・TLSの追加、公開操作の承認をこの記録から推定しない。
